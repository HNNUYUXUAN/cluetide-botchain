# Web3／区块链工程面试讲解

## 两分钟说明

“我做的是准确版本的发布授权与验收系统。AI 或开发者提交制品，审阅者批准具体的 manifest 和 artifact 摘要，执行者消费一次授权，发布器观察交付后签发最终回执。验证者可以脱离应用验收原件与签名。”

先展示三版本历史案例，再演示本地更正、多签批准、消费授权和篡改拒绝。历史 BOT 主网用 v1；本轮独立 v2 使用 Anvil 测试链，生产部署有明确迁移步骤。

| 面试问题 | 工程判断与证据 |
| --- | --- |
| 为什么任务 ID 需要 owner 命名空间？ | 防止抢先登记；绑定 chain、contract、owner、salt，由 msg.sender 校验。见 fuzz 和抢占回归。 |
| 为什么交易成功还不够？ | Safe 外层成功可能伴随内层失败。核对准确 calldata、ExecutionSuccess、见证事件及区块状态。 |
| 为什么 unknown 不写成最终回执？ | 目标写入与链上回执之间没有原子事务。未知状态留在链外 reconciliation_required，观察目标后再签发。 |
| 为什么 ERC-1271 不能完全离线？ | 有效性依赖区块状态；记录区块哈希和时间，离线标记需要链状态。过去观察不能描述为当前 owner 状态。 |
| 如何验证构建？ | 固定 solc-js、Paris 和优化参数，重新编译并比较 ABI 与两种 bytecode，独立保留旧产物。 |
| 如何避免自证可信？ | 验证者独立配置合约、runtime 和 signer；证据包不能指定信任根。 |
| 如何处理崩溃？ | 持久化授权、不可变 staging、目标 marker、原子指针、先回执后状态；四个崩溃点验证恢复不重复发布。 |

链证明授权与签名声明，不证明业务质量。当前 v2 目标是隔离文件存储；生产数据库激活、真实 signer 管理、独立审计和多 RPC 运维属于上线工作。Safe 本轮支持 EOA owners 的单次 reviewer CALL。

后续设计讨论可以围绕持久化交易 outbox、多 RPC 交叉验证、不同目标的幂等性和可信部署配置分发展开。
